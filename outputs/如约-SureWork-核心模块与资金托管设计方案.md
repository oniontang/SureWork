## 如约 SureWork · 企业 × OPC 创作者外包平台 · 核心模块与资金托管设计方案

> 定位补充说明：本文档在《OPC接单平台实现方案.md》基础上深化三个专题——**功能模块划分（含新增的"项目实时预览"）**、**关键实体与数据模型**、**支付宝资金托管与纠纷仲裁的业务逻辑**。支付通道由原方案的"微信+支付宝"收敛为**支付宝为主通道**，理由：预授权冻结 + 商家分账 + 对账体系三者齐备，天然贴合"托管-验收-解冻"语义，MVP 只接一条通道可显著降低联调与对账复杂度。

# 一、核心功能模块划分

## 1.1 模块总览（7 个一级模块）

```
┌─────────────────────── 如约（SureWork）平台 ───────────────────────┐
│ ① 账户与认证模块     双方注册/实名/企业认证/OPC认证/信用分 │
│ ② 需求与撮合模块     需求发布·审核·需求池·投标·邀约派单    │
│ ③ 项目履约模块   ★  订单/里程碑/交付物/项目实时预览/沟通   │
│ ④ 资金托管模块   ★  支付宝预授权冻结/解冻/分账/提现/对账   │
│ ⑤ 合同与仲裁模块 ★   电子合同签署/存证·纠纷工单·平台仲裁   │
│ ⑥ 评价与信用模块     双向互评/晒单/信用分聚合/榜单         │
│ ⑦ 运营支撑模块       机审人审/风控/内容安全/数据看板/客服   │
└──────────────────────────────────────────────────────┘
★ = 本文档重点设计模块（相对原方案新增或深化的部分）
```

## 1.2 各模块功能点与优先级

### ① 账户与认证模块
- 功能点：注册登录（手机号+验证码）、个人实名（二要素+人脸）、企业认证（营业执照+法人授权）、OPC 认证（作品集人工审核+技能证明）、信用分账户、账号设置（信息完善/隐私开关/注销）。
- 优先级：P0（实名与企业认证是托管付款的前置条件）。

### ② 需求与撮合模块
- 功能点：结构化发单（品类/交付物/里程碑建议/验收标准模板）、机审（违禁品类+联系方式检测）+人审、需求池（公开大厅+定向可见）、投标（报价+方案+排期，限 1 次/需求）、邀约派单（历史合作/收藏列表直发）、需求质量评分。
- 优先级：P0 发单/投标/派单；P1 质量评分、智能推荐。

### ③ 项目履约模块（含 ★项目实时预览）
- 功能点：
  - 订单创建（中标→电子合同→托管付款→开工）；
  - 里程碑管理（≥3000 元强制拆分，30/40/30 为默认模板；每个里程碑独立"交付→预览→验收→放款"）；
  - 交付物通道（文件上传/对象存储，源文件放款后解锁）；
  - **项目实时预览（新增）**：见 1.3 专节；
  - 在线沟通（会话绑定订单、结构化卡片、跳单检测、一键平台介入）；
  - 自动验收时钟（交付后 7×24h 未验收自动通过，可按品类配置）。
- 优先级：P0 全部。

### ④ 资金托管模块（支付宝）
- 功能点：见第三章。

### ⑤ 合同与仲裁模块
- 功能点：
  - 电子合同：模板库（居间+承揽服务协议）、e签宝/法大大签署、里程碑条款与验收标准固化进合同附件、签署完成才开始托管付款、合同存证编号回写订单；
  - 纠纷仲裁：见第四章；
  - 售后窗口：结算后 14 天质量售后工单。
- 优先级：P0 电子合同（托管付款的前置）；P0 仲裁基础流；P1 售后工单自动化。

### ⑥ 评价与信用模块
- 功能点：订单关闭前强制互评（匿名双公开）、四维评分、晒作品、信用分聚合（评价+履约行为）、榜单与曝光加权、信用修复。
- 优先级：P0 互评；P1 信用分模型 V2。

### ⑦ 运营支撑模块
- 功能点：审核工单台、仲裁工作台（双人复核）、资金对账台（差异工单）、内容安全 API、举报处理、数据看板（GMV/成交/纠纷率/复购）。
- 优先级：P0 审核与仲裁台（运营兜底）；P1 看板。

## 1.3 ★ 项目实时预览（新增模块专节）

**解决的问题**：设计/开发类项目验收争议的根源是"过程黑箱"——企业直到交付日才第一次看到成果，不满意时已积重难返。实时预览让"预览→批注→修改→验收"形成小循环，把大争议拆解成小反馈。

**形态按品类分三档**：

| 品类 | 预览形态 | 实现要点 |
|---|---|---|
| 设计类 | 在线稿预览：上传 PNG/JPG/PDF 生成版本化预览页，支持逐项批注（框选区域+评论） | 对象存储+图片服务；批注锚点存坐标；预览图自动打水印（"如约 SureWork预览 LC-xxxx·禁止商用"），源文件（PSD/AI/Figma）验收后解锁 |
| 开发类 | 预览环境链接：预发 URL / 仓库提交关联，展示提交记录与截图 | 交付物挂链接+自动截图存档；关键版本快照，避免"链接失效"扯皮 |
| 文档/内容类 | 在线文档预览：md/pdf/office 转预览 | 统一转 PDF 预览，加水印 |

**核心规则**：
1. **版本不可变**：每次交付生成 `preview_version`（版本号+文件指纹+时间），历史版本只读，杜绝"偷换交付物"；
2. **批注即待办**：需求方在预览上的框选批注自动生成"修改请求"，从业者逐条标记已处理，处理记录进入订单事件链（仲裁证据）；
3. **预览≠验收**：预览阶段意见不构成驳回，正式驳回必须在验收环节走结构化驳回（选原因+说明），防止口头承诺无据可查；
4. **权限**：预览仅限订单双方+平台仲裁员；水印预览图外泄可追溯（水印含订单号+用户 ID）。

# 二、关键实体与数据模型

## 2.1 实体关系总览

```
企业 Enterprise ─┐
                 ├─< User 用户 >─┐
OPC 创作者 ──────┘               │
                                 │ 1:N
                ┌────────────────┼──────────────────┐
                ▼                ▼                  ▼
          Demand 需求      Contract 电子合同      CreditLog 信用流水
                │ 1:N                │ 1:1(订单)
           Bid 投标 / Invitation 邀约 │
                │ 中标                │
                ▼                     │
             Order 订单 ◄─────────────┘（合同编号回写）
                │ 1:N
     ┌──────────┼──────────────┬─────────────────┐
     ▼          ▼              ▼                 ▼
Milestone   EscrowOrder    PreviewVersion    Conversation
里程碑        托管单          预览版本           会话
 │ 1:N        │ 1:N           │ 1:N             │ 1:N
 │      SplitRecord 分账单   PreviewComment    Message 消息
 │            │              批注
 │ 0..1
 Dispute 仲裁工单 ──< Evidence 证据 ──> ArbitrationDecision 裁决
                │
          Review 双向评价（订单关闭前）
```

## 2.2 核心实体字段要点

**Order 订单**（聚合根）
```
id, contract_no(合同编号), enterprise_id, opc_id, demand_id
total_amount, commission_rate(默认10%)
status: created→ongoing→delivering→accepting→settled→after_sale→closed
        旁路: arbitrating / cancelled / refunded
auto_accept_deadline(自动验收时间), escrow_status: unpaid|frozen|partial_released|released|refunded
```
要点：`sum(milestone.amount)=total_amount` 为库级校验；escrow_status 与 status 解耦存储。

**Milestone 里程碑**（资金最小单元）
```
id, order_id, seq, title, amount(如 2040/2720/2040)
status: pending→delivering→delivered→accepting→paid / rejected(≤3次)
deliver_time, accept_deadline, reject_count
```

**EscrowOrder 托管单**（与支付宝交互的核心，见第三章）
```
id, order_id, milestone_ids[], amount, alipay_auth_no(预授权单号)
status: created|frozen|releasing|released|refunding|refunded|partial
channel_trade_no, freeze_time, release_time, refund_no
```

**SplitRecord 分账单**
```
id, escrow_id, receiver_type(opc|platform), receiver_id, amount, ratio
flex_worker_no(完税单号), status: init|success|fail|returned
```

**PreviewVersion 预览版本 / PreviewComment 批注**
```
preview: id, milestone_id, seq, files_json(oss_key+指纹), watermark_no, created_by, immutable
comment: id, preview_id, anchor_json(页码/坐标/区域), content, status: open|resolved|wontfix, resolved_evidence
```

**Contract 电子合同**
```
id, order_id, template_id, esign_flow_id(签署流程号), parties_json
status: generating|signing|signed|voided, signed_file_oss, evidence_no(存证编号)
```

**Dispute 仲裁工单**
```
id, order_id, milestone_id, initiator, type: quality|delay|scope_change|payment
status: filed→evidencing→negotiating→arbitrating→decided→executed→closed
        旁路: withdrawn
handlers_json(双人复核), decision_type, split_amount, sla_deadline
```

**其余实体**：User/Demand/Bid/Invitation/Conversation/Message/Review/CreditLog 与原方案一致，不再重复。

## 2.3 两条主干状态机

**订单 × 里程碑（履约主线）**
```
created ──合同签署+首期冻结──▶ ongoing ──从业者交付──▶ delivered
   ◀── 驳回(≤3次,附整改要求) ──┤
deliverable ──需求方验收通过 或 7×24h 自动通过──▶ milestone paid → 分账
全部里程碑 paid ──▶ settled ──14天售后──▶ closed（互评强制）
```

**托管单（资金主线）**
```
created ──支付宝预授权成功──▶ frozen ──验收通过──▶ releasing ──分账成功──▶ released
   │                                                │ 分账失败
   └── 退款/裁决退款 ──▶ refunding ──▶ refunded ◀────┘ → 人工补偿工单
```

# 三、资金托管安全业务逻辑（支付宝）

## 3.1 托管方案选型

| 方案 | 机制 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 支付宝预授权+转支付 | 下单时对付款人做**预授权冻结**（花呗/余额/银行卡），验收后**解冻转支付**给平台/分账给 OPC | 资金始终在支付宝体系内冻结，语义上是"真托管"，平台账上无资金沉淀 | 需申请预授权产品权限；用户感知"冻结额度"需教育 | **MVP 首选** |
| B. 支付+备付金监管户+延时分账 | 货款进入支付宝/网商银行监管户，验收后调商家分账 | 用户体验与普通付款一致；支持对公 | 平台需严格按"待结算资金"管理，合规依赖分账产品资质 | 预授权未获批时的备选 |
| C. 淘宝式担保交易 | 确认收货后放款 | 零开发心智 | 不支持里程碑拆分与分账 | 不采用 |

**MVP 采用 A**：每个订单（或首期）创建一笔预授权，冻结期上限 90 天（支付宝预授权有效期），超长项目按里程碑分别创建预授权（每期开工前再冻结下一期，见 3.3）。

## 3.2 资金时序（正常流）

```
1  企业确认订单 → 平台生成合同 → 双方签署(电子签)
2  创建 EscrowOrder → 调支付宝预授权接口 → 用户确认(免密代扣式确认页) → 冻结 ¥6,800
   · 回调写入 alipay_auth_no，EscrowOrder=frozen，Order=ongoing
3  M1 交付 → 预览批注小循环 → 验收通过（或 7×24h 自动通过）
4  平台调用「预授权转支付」：¥2,040 解冻并支付到平台商户号
   → 同步发起商家分账：¥1,836 → OPC 收款账户（绑定支付宝/银行卡）
                    ¥204  → 平台佣金账户
   → SplitRecord=success，Milestone=paid
5  M3 完成、售后窗口结束 → 剩余预授权自动解冻转支付或按需冲退
6  T+1 定时对账：支付宝对账单 vs 本地 payment/split 记录逐笔核对
```

## 3.3 资金安全规则（铁律）

1. **平台不碰钱**：平台商户号只在分账瞬间过账，不设自有资金池；预授权冻结在支付宝，平台无权挪用。
2. **先签合同再冻结**：无 signed 合同的订单不允许创建预授权（接口层强校验）。
3. **放款三要素**：里程碑验收通过 + 合同在途有效 + 分账接收方实名一致（支付宝实名=平台实名认证姓名），任一不满足不放款。
4. **幂等与防重复放款**：预授权转支付/分账均带幂等键（escrow_id+milestone_seq）；本地事务表先落库再调接口，回调驱动状态推进。
5. **退款原路**：预授权解冻前可直接解冻（资金不落任何一方）；已分账部分需先走「分账回退」，失败转人工追偿并扣信用分。
6. **预授权过期风控**：冻结满 80 天未放款的托管单进入监控清单，自动提醒双方+运营；必要时协商重新授权。
7. **对账与差异处理**：日终对账三类差异（掉单/多账/金额不符）自动生成人工工单；掉单以支付宝账单为准补单。
8. **提现与完税**：OPC 收款账户绑定本人实名支付宝；分账到账后由灵活用工平台代征个税，完税单号回写 SplitRecord.flex_worker_no。

## 3.4 异常流

- 用户支付中断/冻结失败 → EscrowOrder=created 保留 30 分钟，超时关闭订单；
- 分账接口超时 → 状态置 releasing + 定时重试（幂等），3 次失败转人工；
- 需求方支付宝账户异常（被风控）→ 冻结单不受影响，仍可正常验收放款；
- OPC 换绑账户 → 换绑后 48 小时内冻结放款（防盗刷换卡）。

# 四、纠纷处理业务逻辑（平台介入仲裁）

## 4.1 仲裁触发入口（谁可以发起、什么时候）

| 入口 | 触发条件 | 资金动作 |
|---|---|---|
| 需求方"验收驳回"达 3 次 | 第 3 次驳回后任意一方可申请 | 争议里程碑对应预授权额度**立即冻结（保持 frozen）** |
| 任一方"申请平台介入" | 存在未决里程碑即可 | 同上 |
| 自动验收前申诉 | 需求方在自动验收时钟到期前申请 | 时钟**暂停**，进入仲裁 |
| 售后期举报 | 结算后 14 天内 | 已放款部分不冻结，走追偿流程 |

**不受理**：口头承诺无留痕、验收标准未填写的需求（发单强制填写验收标准正是为此）、已过售后期。

## 4.2 仲裁流程与 SLA

```
filed 立案（0.5 工作日）
  → evidencing 举证期（双方各 48h，提交：合同条款、预览版本记录、
     批注处理记录、聊天记录、交付物比对——全部来自订单事件链，
     不接受线下补交材料）
  → negotiating 平台调解（1 个工作日，调解员给出和解方案，
     双方接受则按和解金额执行，流程终止）
  → arbitrating 仲裁（2 个工作日，双人复核制：两名仲裁员独立出具
     意见，不一致时交仲裁组长终审）
  → decided 裁决书生成（依据+金额拆分，双方可见）
  → executed 执行（调支付宝接口：按裁决比例解冻转支付/退款）
  → closed 结案（回写双方信用分：败诉方扣分，恶意发起方额外扣分）
```

**全程 SLA：立案到结案 ≤ 5 个工作日**；期间自动验收时钟暂停，订单不可被删除。

## 4.3 裁决类型与执行

| 裁决 | 执行动作 |
|---|---|
| 全额放款 | 争议里程碑预授权解冻转支付 → 正常分账 |
| 部分放款 | 按 70/50/30 等比例拆分：放款部分走分账，剩余部分解冻退回企业 |
| 全额退款 | 预授权直接解冻退回（资金未落 OPC 账户，无追偿成本） |
| 各打五十大板 | 同部分放款，比例写入裁决书 |
| 恶意单认定 | 退款 + 发起方信用分 -50 + 限流 30 天 |

**已分账后的追偿**（售后期纠纷）：优先协商回退；协商不成由平台先行垫付退款给企业（体验优先），再向 OPC 追偿（从后续分账扣回 + 法律手段），这是引入"平台先赔"的前提条件——只有 L2 以上认证 OPC 才享受高授信。

## 4.4 防滥用机制

- **举证即封存**：立案后订单事件链只追加不修改，双方不能再上传替换文件；
- **恶意仲裁成本**：败诉方承担信用扣分；一年内 3 次恶意发起者禁用仲裁入口；
- **仲裁透明度**：脱敏后的裁决摘要进入"仲裁公示页"，建立平台判例库，让双方对规则有稳定预期；
- **升级通道**：对裁决不服可在 7 天内申诉一次，由仲裁组长终审，终审为最终结果（协议中已约定）。

# 五、落地优先级（对 MVP 计划的修订）

1. **P0（MVP 必须）**：支付宝预授权托管 + 里程碑放款 + 电子合同签署 + 基础仲裁流（立案/举证/裁决/执行）+ 预览版本化（设计类水印预览）；
2. **P1（上线后 1–2 月）**：批注待办闭环、调解环节产品化、分账失败自动重试看板、开发类预览环境；
3. **P2（规模化后）**：智能推荐、平台先赔池、仲裁判例库公开、多通道（微信）扩展。
